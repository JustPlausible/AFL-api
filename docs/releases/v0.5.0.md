# AFL-api v0.5.0 release notes

These notes describe the implemented v0.5.0 repository state and are intended
to be reused for a future GitHub Release. **They do not mean that v0.5.0 has
been tagged or released.** The live CFS, injury, Docker, and other manual gates
in the release-readiness documents remain open.

## Highlights and operational source policy

v0.5.0 establishes an explicit, shared source-selection boundary for Scheduler
and Admin jobs. Public AFL JSON is preferred for competitions, seasons, teams,
rounds, fixtures and match lifecycle detail. Champion Data/CFS JSON supplies
season-player listings, read-only match rosters, and the operational match
player-stat path. Rendered AFL HTML remains deliberate for injuries, persisted
lineups, player enrichment, and explicit legacy match/stat diagnostics.

There is **no automatic JSON-to-HTML fallback**. Unpublished CFS data is
reported unavailable without a destructive write; authentication, transport,
payload, programming, and persistence failures fail the operation. HTML paths
must be selected explicitly or assigned by the domain policy. Scheduler and
Admin use the same policy functions; the CLI identifies preferred structured
commands and explicit legacy HTML commands rather than silently changing
sources. The complete matrix is in the [operational source policy](../operational_source_policy.md).

These upstream roles are intentionally distinct:

* Public AFL JSON supplies the canonical competition/season hierarchy and AFL
  fixture metadata. The endpoints are public but undocumented, so fixtures and
  contract tests reduce—not eliminate—change risk.
* CFS supplies Champion Data identities, season players, rosters, and a richer
  source-specific statistics contract. Some resources require authentication,
  may be unpublished, incomplete, or unavailable, and do not carry a promised
  stable public contract.
* HTML fills domains without demonstrated structured parity. It is not assumed
  to be inferior accidental legacy code, but selectors and page structure can
  change without notice.

## Canonical season and player bootstrap

Run `python cli.py --bootstrap-afl-season SEASON` after migrations on a fresh
database and whenever the target season requires bootstrap. It first collects
and persists public AFL competition, season, round, team, and match metadata,
then collects the CFS season-player listing. The public AFL hierarchy owns the
canonical season/team context; `canonical_players` provides internal identity,
while provider IDs are retained in a namespaced crosswalk. Season membership,
team links, and the AFL/Champion Data mappings are persisted transactionally.

Downstream canonical injury matching and canonical links from CFS statistics
depend on those player and season records. Consequently, migration must precede
bootstrap and bootstrap must precede those imports on a fresh database. Missing
or contradictory provider/team mappings are diagnosed rather than silently
invented or reassigned. CFS roster collection remains read-only and is not a
substitute bootstrap path.

## Canonical injury persistence

Injuries deliberately continue to come from rendered HTML because no suitable
structured source has been proven. Scraped, human-edited player names are
normalised and matched within the applicable canonical club/season roster.
Documented aliases and formatting variants can resolve, but identity resolution
is not perfect: ambiguous players, unknown names, wrong-club candidates, or
players without AFL provider IDs remain unresolved.

Only resolved rows are written to current/history injury persistence. A mixed
result continues with valid rows, returns a `partial` summary, and reports
resolved, persisted, unresolved, and ambiguous counts plus per-row diagnostics.
No synthetic player identity is created for a rejected row.

## Database migrations 0009–0011

Migration files are immutable and applied in numeric order by the repository
migration runner:

* `0009_canonical_player_seasons.py` creates `canonical_players`, the
  provider-namespaced `player_provider_ids` crosswalk, `afl_team_seasons`, and
  `competition_season_players`, plus supporting indexes. It adds a nullable
  `canonical_player_id` foreign-key column and index to `cfs_player_stats`; it
  does not replace the older player or statistic tables.
* `0010_refresh_canonical_club_seed.py` reruns the validated canonical club-seed
  upsert so verified identifier and alias edits reach existing databases. It
  updates matching seeded club rows but does not delete unrelated rows.
* `0011_partial_scrape_runs.py` rebuilds `scrape_runs` so its status constraint
  also accepts `partial`, copies all existing rows, drops the old table, and
  recreates its indexes. The table rebuild is operationally significant and no
  down migration is provided.

The API currently invokes migrations during application import/startup, while
operators can and should apply them explicitly during a controlled upgrade with
`python -m db.migrate` (the compatible `python -m db.init_db` entry point also
remains). Fresh databases receive the full sequence; recognized v0.3.0 databases
are baselined then upgraded, while unexpected/partial schemas fail safely.
Applied checksums prevent migration files being rewritten unnoticed. Back up
SQLite before upgrading: the forward-only runner provides transaction safety,
not an automatic downgrade or restoration path.

## Scrape audit coverage is partial

Scrape-run records distinguish invocation lifecycle (`running`, `completed`,
`partial`, or `failed`) and can carry rows read/written, target, trigger, error,
and scheduler correlation information. Operational policy paths record source
selection diagnostics, and canonical injury persistence exposes rejected-row
counts. This supports collection and persistence diagnosis but is **not complete
observability**.

Audited entry points include operational public-JSON refresh/status, CFS player
statistics, HTML injuries/lineups, and the principal fixture/match/legacy-stat
paths. Where collectors provide accurate counts, parsing/collection and writes
can be compared; match refreshes may intentionally leave counts null. A
`completed` collection alone does not prove every payload record parsed or
persisted, and older/direct helper paths are not retroactively covered.
Rejected CFS records use collector diagnostics; injury unresolved/ambiguous
records use partial summaries. Not every parser has per-record rejection
instrumentation, and existing `scrape_log`/`scrape_summary` records remain
separate rather than being backfilled into `scrape_runs`.

## CLI and documentation improvements

`python cli.py --version` prints only the authoritative version. The preferred
structured commands are `--collect-afl-metadata`,
`--bootstrap-afl-season`, `--collect-match-rosters`, and
`--collect-match-player-stats`. Metadata inspection and roster collection are
read-only; bootstrap persists canonical metadata/player membership, and match
player statistics persist `cfs_player_stats`. `--print-json` controls diagnostic
output and does **not** disable persistence; `--afl-raw-directory` optionally
retains credential-free raw responses. CFS commands validate opaque `CD_R...`
or `CD_M...` identifiers, while `--source-status` and `--afl-match-id` support
explicit match-status reconciliation.

Explicit HTML operations remain available as `--scrape-injuries`,
`--scrape-lineups`, `--scrape-round`, `--scrape-all-rounds`, and
`--scrape-match`, alongside legacy club import/export, scrape, and enrichment
tools. Scheduler/Admin statistics use the same CFS operational path; their
lineup and injury jobs intentionally use the shared HTML policy. See the
[CLI guide](../cli.md), [source policy](../operational_source_policy.md), and
[scrape audit guide](../scrape_run_audit.md).

## Deliberate HTML boundaries

Injury pages, operational lineup persistence, and player enrichment/listing
gaps still use rendered HTML. Explicit legacy fixture, match-centre statistics,
and diagnostic tools also remain available, but are not automatic fallback.
HTML is retained where structured parity or persistence is absent, not because
v0.5.0 claims a completed JSON migration. Selectors, client-rendering behavior,
publication timing, labels, and page structure are upstream fragility points.

## Why `player_stats` and `cfs_player_stats` both exist

The tables represent different source and persistence contracts.
`player_stats` is written by the explicit legacy rendered match-centre command
and retains its legacy AFL-facing schema. `cfs_player_stats` is written by the
operational authenticated CFS collector, retains provider IDs/source payload
semantics, and can link observations to canonical players after bootstrap.
Neither replaces the other in v0.5.0; there is no reconciliation or dual write.
Callers must select according to source provenance and required fields rather
than treating rows or statistics as interchangeable.

## Operator upgrade checklist

Use the detailed [v0.5.0 release/rollback runbook](../operations/release_runbook_v0_5_0.md).
At minimum:

1. Quiesce API, Scheduler, Admin, CLI, migration, and direct scraper writes.
2. Back up the SQLite database with a WAL-safe method and retain relevant
   deployment configuration/secrets through the deployment's secure process.
3. Apply and verify migrations with `python -m db.migrate`; confirm migration
   records through `0011` and run integrity/foreign-key checks from the runbook.
4. Run `python cli.py --bootstrap-afl-season SEASON` when establishing the
   canonical target season, after migrations and with required upstream access.
5. Validate `python cli.py --version`, CLI diagnostics, API health/OpenAPI, and
   the deployment-specific Scheduler/Admin health checks.
6. Review unresolved/ambiguous injury diagnostics, rejected collector records,
   and recent `scrape_runs`; do not equate collection success with complete
   persistence.
7. Keep the previous database and immutable prior application revision until
   validation succeeds. Restore the verified database backup if forward writes
   make application-only rollback unsafe.

## Known limitations

Upstream limitations include undocumented public AFL endpoints, authenticated
or unavailable CFS resources without a stable published contract, delayed or
partial records, changing rendered HTML, human-edited injury names, and sources
that omit a stable player identifier. Project limitations include incomplete
per-record audit coverage, deliberately read-only CFS rosters, no automatic
fallback, incomplete structured parity for HTML domains, and two
source-specific statistic models that cannot be compared as identical schemas.

Live CFS authentication/availability, live injury-page behavior, deployed image
and Compose behavior, and full production rollback remain manual release gates.
Accordingly, claims that could not be established offline are qualified here;
no guarantee of upstream availability, completeness, identity resolution, or
full observability is made.
