# AFL-api v0.6.0 release notes

These notes describe the implemented v0.6.0 repository state and are intended to accompany the `v0.6.0` GitHub Release.

v0.6.0 is a significant development release following v0.5.0. It extends the canonical AFL/CFS collection model into a versioned consumer API, introduces whole-season synchronization and reconciliation tooling, and substantially strengthens Scheduler durability, lifecycle-aware CFS polling, SQLite coordination, recovery, auditability, and operator workflows.

The release retains the established source-authority principle: public AFL JSON, authenticated CFS JSON, and rendered AFL HTML remain distinct acquisition sources with explicit domain ownership. There is still no silent JSON-to-HTML fallback or automatic dual-write between legacy and canonical statistic stores.

## Highlights

### Versioned `/api/v1` consumer API

v0.6.0 introduces the first supported versioned consumer API.

The navigation chain is:

```text
GET /api/v1
    -> GET /api/v1/seasons
        -> GET /api/v1/seasons/{season_id}/rounds
            -> GET /api/v1/rounds/{round_id}
            -> GET /api/v1/rounds/{round_id}/matches
                -> GET /api/v1/matches/{match_id}
                    -> GET /api/v1/matches/{match_id}/player-stats
```

The v1 API is consumer-focused and projects reviewed canonical fields rather than exposing provider payloads, raw JSON, Scheduler state, or persistence internals.

The player-stat resource reads authoritative `cfs_player_stats`, resolves canonical player and AFL identities where available, and exposes the stable AFL statistic set: goals, behinds, kicks, handballs, disposals, marks, tackles, and hitouts.

Match player-stat responses distinguish `final`, `partial`, and `not_available`. Finality is calculated from persisted authoritative evidence rather than inferred solely from match status.

Normal responses expose consumer-facing information plus resource-level `metadata.source_updated_at`. Selected provenance is available through `?advanced=true` and requires the `advanced-read` API-key capability.

The existing unversioned `/api/...` routes remain compatibility endpoints in v0.6.0 and have not been silently repointed to the new canonical models.

## API-key capabilities

API keys now support named capabilities. Implemented capability names are `standard-read` and `advanced-read`.

Existing and newly created keys receive `standard-read` by default. Advanced provenance on supported v1 resources requires an explicit `advanced-read` grant.

Operator commands include:

```bash
python cli.py --grant-api-key-capability <LABEL> advanced-read
python cli.py --revoke-api-key-capability <LABEL> advanced-read
python cli.py --add-api-key <LABEL>
python cli.py --list-api-keys
python cli.py --remove-api-key <KEY_OR_LABEL>
```

Full keys continue to be displayed only at creation and stored only as secure hashes plus administrative prefixes.

A nullable rate-limit model exists in persistence, but runtime rate limiting is not implemented in v0.6.0.

## Whole-season synchronization

v0.6.0 adds the persistent whole-season workflow:

```bash
python cli.py --sync-afl-season <SEASON_YEAR>
```

The synchronizer composes the existing source-authority and persistence boundaries rather than introducing a second collection stack. It bootstraps canonical public AFL metadata, collects and persists the CFS season-player population, selects persisted matches, reconciles lifecycle where required, collects eligible authoritative CFS match-player statistics, persists accepted snapshots to `cfs_player_stats`, and records correlated per-season and per-match audit evidence.

By default, already-complete concluded matches are skipped. Explicit refresh and round/match bounds are available for controlled reprocessing.

Failures are isolated per match where safe. Collection, persistence, and audit outcomes remain distinct so an audit-finalisation failure cannot falsely imply that already committed authoritative statistics were rolled back.

No season-sync path writes the legacy HTML `player_stats` table.

## Season completeness and reconciliation reporting

A read-only operator report is available:

```bash
python cli.py --report-afl-season <SEASON_YEAR>
```

The report inspects the existing SQLite database in query-only mode and evaluates canonical season foundations, rounds and matches, match lifecycle, authoritative `cfs_player_stats` coverage, snapshot authority/finality, canonical players and provider mappings, competition-season membership, team relationships, and relevant scrape/audit evidence.

Human-readable and `--print-json` output share the same underlying result. The report performs no upstream network calls and makes no database changes.

## Improved bootstrap operator experience

`--bootstrap-afl-season` remains the supported canonical initialisation and player-membership refresh path.

Its default output is now a concise human-readable summary rather than a full JSON object. The summary includes the selected season and persisted entity counts and points operators toward `--report-afl-season` as the natural verification step.

Full structured output remains available with `--print-json`. Persistence semantics are unchanged.

## Lightweight and stricter CLI

The root CLI now has a clearer split between argument handling and runtime execution. `cli.py` remains lightweight for `--help` and `--version`, while heavier runtime handlers live in `cli_runtime.py` and are imported only after argument validation.

Only one top-level operation may be selected per invocation. Conflicting workflow flags fail through the normal argparse error path before database, browser, or upstream runtime dependencies are loaded.

Collection commands also share a common diagnostic envelope so public AFL JSON, CFS JSON, database-free collection, HTML collection, persistence, and failure states are presented consistently.

## Database-free collection orchestration

The database-free collection workflow is a maintained operator tool:

```bash
python cli.py --collect-afl-data ...
```

It can combine supported public AFL and CFS endpoint families and write deterministic `request.json`, `summary.json`, `raw/`, and `normalised/` artifacts without opening the application database.

Unsupported investigated families are reported explicitly as skipped rather than appearing successful. This workflow is useful for upstream validation, fixture investigation, and source-contract testing without affecting persisted application state.

## Scheduler architecture and lifecycle-aware player-stat polling

The Scheduler has changed substantially since v0.5.0. APScheduler remains the clock/wake-up mechanism, but lifecycle-driven CFS match-player-stat collection now uses durable application state rather than relying only on transient interval jobs.

### Durable match-stat windows

Migration `0013` adds `match_stat_windows`, which persists per-match polling-series state including canonical and provider match identity, resolved lifecycle, collection phase, next due time, cadence/profile, attempt counters, consecutive failures, last success/write information, snapshot authority/finality evidence, bounded lease ownership, and diagnostic state.

This allows planning state to survive Scheduler restarts.

### Conservative CFS polling

Lifecycle-aware CFS polling is implemented with conservative defaults. The worker is disabled by default until explicitly configured, requires lifecycle evidence before live polling, defaults live polling to approximately 60 seconds before deterministic jitter, uses bounded collection/network concurrency, keeps Scheduler database writes serialized, performs network requests outside SQLite write transactions, applies bounded retry/backoff behaviour, handles CFS authentication refresh and process-level authentication cooldown, never falls back to HTML, never dual-writes the legacy `player_stats` table, and prevents a final authoritative snapshot from being overwritten by a lower-authority later observation.

A concluded match alone does not close player-stat collection. Completion requires committed authoritative concluded coverage.

## Scheduler recovery

Interrupted player-stat polling is explicitly recoverable.

Migration `0014` and `scheduler/recovery.py` correlate match windows, Scheduler registry attempts, scrape runs, persisted CFS player-stat evidence, and Scheduler runtime instances.

Interrupted attempts are classified using persisted evidence rather than inferred from free-form errors or elapsed time. Recovery preserves historical attempts and uses explicit machine-readable states including `interrupted`, recovery reason, persistence evidence, and supersession links.

A dry-run operator interface is available before mutation:

```bash
python -m scheduler.recovery --dry-run ...
```

Unknown outcomes remain unresolved rather than being guessed as successful or failed.

## Scheduler lifecycle synchronization fixes

Live testing identified and resolved Scheduler edge cases before v0.6.0.

Startup recovery for an already-LIVE match now uses the configured match-day timezone rather than an undefined timezone constant.

Active match-stat windows are reconciled immediately when canonical match lifecycle advances. Polling workers re-read canonical match status instead of relying only on stale lifecycle state captured when a lease was claimed. This prevents a match that has advanced to `CONCLUDED` from continuing indefinitely under a stale `LIVE` polling phase.

## Timezone-safe planning

Scheduler planning treats source timestamps as explicit instants. Naive, malformed, or missing timestamps are rejected rather than having a timezone guessed.

`AFL_MATCH_DAY_TIMEZONE` controls application match-day boundaries and defaults to `Australia/Perth`.

Planning failures are persisted as safe diagnostic registry records and can be inspected by operators. Scheduler planning no longer relies on SQLite host-local `localtime` semantics for AFL match-day selection.

## SQLite coordination and Scheduler write lane

v0.6.0 formalises the supported SQLite execution model.

The database connection layer applies an explicit SQLite policy including WAL and busy-timeout behaviour. Scheduler persistence is routed through a single serialized write lane. Network acquisition and parsing occur outside write transactions, and the lane opens short-lived policy-controlled connections for persistence callbacks.

The supported deployment continues to assume one shared SQLite database, one active Scheduler process, short write transactions, serialized Scheduler writes, and API/Admin readers and controlled writers sharing the same database directory.

`AFL_SCHEDULER_REPLICAS=1` is enforced as the supported Scheduler deployment model.

This improves contention behaviour but does not turn SQLite into a multi-writer distributed database.

## Scrape and decision audit improvements

Audit records provide stronger correlation across whole-season synchronization and Scheduler collection.

Season sync records machine-readable skip decisions such as already complete, scheduled, live/postgame, future placeholder, missing provider identity, unresolved lifecycle, and requested match not found. Decision rows carry stable reason codes and share correlation IDs with their parent season run.

Scheduler polling attempts likewise retain window, lease, attempt, and scrape-run relationships. Sensitive values remain redacted from diagnostic and audit summaries.

## JSON source-contract regression fixtures

The AFL JSON/CFS integration has a larger deterministic offline fixture corpus covering competitions, competition seasons, rounds, teams, matches, match detail, player ID mapping, season players, match rosters, match player statistics, and known CFS error states.

Contract tests exercise production collectors and normalisers while blocking network access and checking fixtures for authentication material. Required-record validation was strengthened so malformed public records fail locally and visibly rather than being silently accepted.

These fixtures reduce provider-schema regression risk but cannot guarantee that undocumented upstream services will remain stable.

## Player-stat team identity clarification

Verified CFS `playerStats/match` responses do not currently contain an independent team provider identifier for each returned player-stat observation.

v0.6.0 therefore does not infer or synthesise `team_provider_id` from undocumented fields or array position. An incoming null source-side team-provider value also does not erase a previously verified stored value.

Consumer `/api/v1` team identity is instead resolved from player-stat side to canonical match to canonical home/away team. This distinction is intentional.

## Injury collection pipeline

The rendered-HTML injury source remains operational, but its implementation is separated into explicit acquisition, parsing, canonical identity resolution, persistence, and orchestration stages.

The shared operational source policy invokes the modular injury pipeline and preserves partial-result semantics.

No maintained structured injury endpoint has yet been proven suitable, so Playwright-backed acquisition remains intentional in v0.6.0.

## Production-like Compose guidance

The repository distinguishes development and production-like Compose examples.

`compose.example.yaml` is explicitly development/evaluation-oriented. `compose.production.example.yaml` provides a safer single-instance starting point with one shared immutable image tag, no source bind mount, no Uvicorn `--reload`, shared persistent data/log volumes, consistent `DB_PATH`, API/Admin published as appropriate, Scheduler not published to the host, and a single Scheduler replica.

This remains an example rather than a complete production deployment specification.

## Consumer-neutral project scope

Project documentation explicitly describes AFL-api as a consumer-neutral data collection and access service.

Consumer-specific scoring, league logic, and presentation remain downstream concerns rather than responsibilities of AFL-api. A small number of legacy-compatible names or filenames may remain where changing them would unnecessarily break compatibility.

## Database migrations 0012–0015

v0.6.0 adds four migrations after the v0.5.0 sequence.

- `0012_season_sync_decisions.py` extends `scrape_runs` with structured season-sync decision evidence and relevant indexes.
- `0013_match_stat_windows.py` adds durable match-player-stat polling/window state and lease information.
- `0014_interrupted_attempt_recovery.py` adds interrupted-attempt recovery/correlation fields and Scheduler runtime-instance state.
- `0015_api_key_capabilities.py` adds normalized API-key capabilities and the nullable future rate-limit field.

Migrations remain forward-only and checksum-protected. Back up the SQLite database before upgrading. Application rollback after migrations or post-upgrade writes may require restoring the verified pre-release database rather than merely reverting the application image.

## Breaking and compatibility considerations

v0.6.0 is largely additive, but operators and consumers should note several behavioural boundaries.

### `/api/v1` is the new stable consumer contract

Consumers should prefer `/api/v1` for new integrations. Existing unversioned `/api/...` endpoints remain available in this release but should be treated as compatibility surface rather than the design target for new consumers. No unversioned endpoint is silently repointed to canonical v1 persistence.

### Player-stat models remain separate

`player_stats` and `cfs_player_stats` still represent different contracts.

The compatibility route `GET /api/player-stats` continues to read legacy rendered-HTML `player_stats`. The versioned route `GET /api/v1/matches/{match_id}/player-stats` reads authoritative CFS `cfs_player_stats`. Rows must not be treated as interchangeable.

### API-key advanced metadata is opt-in

Existing standard keys continue to work for normal v1 reads. A request for `?advanced=true` without `advanced-read` returns a structured `403`.

### CLI permits one operation per invocation

Commands that previously supplied multiple top-level operation flags now fail validation rather than dispatching ambiguously.

### Scheduler deployment remains single-instance

Running more than one Scheduler process against the same configured database is not a supported scaling strategy in v0.6.0.

### New migrations are forward-only

Downgrading application code without considering migrations `0012`–`0015` and post-upgrade writes is not a complete rollback plan.

## Known limitations

- The AFL public JSON and CFS endpoints used by the project do not provide a stable public compatibility guarantee. Fixture and contract testing cannot prevent upstream removal, schema changes, authentication changes, or publication delays.
- CFS `matchRosters/round` has a maintained collector but still does not have canonical application persistence. Operational lineup persistence continues to use rendered AFL HTML until CFS roster/lineup semantics and identity parity are proven.
- Discovered CFS endpoints including `matchRoster/full`, `matchItem`, `matchInterchange`, `commentaryFeed`, and Stats Centre player queries are investigation-only and are not maintained AFL-api collectors in v0.6.0.
- Canonical player identities and season membership are persisted, but v0.6.0 does not expose a dedicated `/api/v1/players` resource.
- Injuries and lineups remain outside `/api/v1` and continue to use compatibility API routes.
- Injuries and operational lineups still rely on rendered page structure and remain vulnerable to upstream HTML changes.
- Runtime API-key rate limiting is not implemented.
- SQLite remains the supported single-database architecture and does not provide distributed locking, multi-primary writes, or horizontally scaled Scheduler execution.
- High-frequency Scheduler polling remains deliberately conservative.
- A match being `CONCLUDED` does not guarantee that a complete authoritative player-stat snapshot has already been published or collected.
- Null source-side `team_provider_id` values are expected with currently verified CFS player-stat responses. Consumer team identity remains resolvable through match side and canonical match/team relationships.
- Failure of a structured preferred source does not silently activate an HTML collector.

## Upgrade notes

For a controlled v0.5.0 to v0.6.0 upgrade:

1. Merge and identify the exact v0.6.0 release SHA.
2. Stop or drain application writers.
3. Take and verify a WAL-safe SQLite backup.
4. Build the immutable application image from the exact release SHA.
5. Apply migrations through `0015`.
6. Verify SQLite integrity and foreign keys.
7. Run or refresh the target season bootstrap if required.
8. Run `python cli.py --report-afl-season <SEASON_YEAR>` and investigate material findings.
9. Verify API-key capability state, particularly keys that require advanced v1 metadata.
10. Start API and verify health/readiness and `/api/v1`.
11. Start the single Scheduler using reviewed polling controls.
12. Inspect Scheduler match windows, recent audit state, and recovery status.
13. Validate live collection conservatively before relaxing any feature flag, allowlist, or cadence.
14. Retain the previous immutable application revision and verified pre-release database backup until validation is complete.

## Release validation

The automated suite expanded substantially during the v0.6.0 development cycle, with final pre-release work reporting more than 700 passing tests.

The release includes deterministic coverage for public AFL/CFS contract parsing, canonical player/stat persistence, whole-season synchronization, completeness reporting, source policy, SQLite coordination, Scheduler match-window planning, lifecycle-aware CFS polling, interrupted-attempt recovery, API-key administration and capabilities, and `/api/v1` authentication and response contracts.

Automated tests are predominantly offline and deterministic. Live AFL/CFS availability, rendered HTML behaviour, real deployment topology, and production database contention must still be validated in the deployment environment.

## Release summary

v0.6.0 moves AFL-api from a primarily collection-focused v0.5.0 foundation to a system with three substantially more complete product boundaries:

1. **Collection and persistence** — public AFL and CFS sources with explicit authority and whole-season reconciliation.
2. **Durable operations** — lifecycle-driven Scheduler planning, bounded polling, serialized SQLite persistence, audit correlation, and crash recovery.
3. **Consumer access** — a typed, versioned `/api/v1` navigation and authoritative player-stat contract.

The release intentionally leaves several boundaries unresolved rather than overextending the architecture: CFS roster persistence, canonical player listing, v1 injuries/lineups, runtime API rate limiting, and investigated match-event/commentary sources remain future work.
