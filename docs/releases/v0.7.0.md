# AFL-api v0.7.0 release notes

These notes describe the implemented change from the v0.6.0 release commit
(`292a5ce`) to the v0.7.0 candidate. The release artifact must record its own
exact SHA; commit names and issue descriptions are not substitutes for that
record.

v0.7.0 is an additive expansion of the canonical collection and `/api/v1`
surface. It promotes several previously investigative CFS datasets into
maintained persistence and read APIs, adds player navigation and telemetry,
and strengthens operator visibility. It does not repoint the legacy HTML
tables or unversioned compatibility routes.

## Consumer API and canonical data

The authenticated discovery response at `GET /api/v1` reports the running
application version. In addition to the v0.6.0 season, round, match, and match
player-stat navigation, v0.7.0 provides:

- canonical player lookup and search, player season/team history, and a
  `canonical_player_id` filter on match player statistics;
- chronological, canonically linked match commentary;
- current and event-history views of match interchange state;
- current injuries with canonical player/team links where identity was
  resolved; and
- CFS match rosters/selections with source change context.

Roster selections are not participation evidence. Actual participation and
statistics remain the responsibility of `cfs_player_stats`. Likewise,
unresolved injury identities are omitted from the canonical injury response
rather than guessed.

The roster work is present in this candidate: canonical roster persistence,
the recurring production collector, and
`GET /api/v1/matches/{match_id}/rosters` landed together in commit `df085ac`
(the merged implementation corresponding to the intended Issue #219 scope).

## Collection and match lifecycle

- Commentary and interchange have separate diagnostic evidence stores and
  maintained production stores. The production Scheduler collects eligible
  live data; commentary includes a bounded recent-live/POSTGAME window, while
  interchange performs one persisted POSTGAME reconciliation poll and then
  stops. Captured evidence supports the interchange freeze rule at the
  LIVE-to-POSTGAME transition.
- Accepted CFS player-stat changes now produce append-only field history and
  sparse period checkpoints while `cfs_player_stats` remains the authoritative
  current/final snapshot.
- Match lifecycle gained a normalized internal period model. Diagnostic
  `matchItem`, interchange, and commentary profiles can capture bounded
  evidence without becoming production source authority.
- Injury acquisition and parsing tolerate the observed partial-team finals
  page while retaining observed-team authority. Canonical identities are
  persisted only when deterministically resolved.
- CFS URL construction now models `/cfs` as the service root. The
  `commentaryFeed` exception remains explicit rather than being accidentally
  joined below that root.

No collector silently falls back from its declared JSON authority to rendered
HTML, and canonical writers do not dual-write legacy tables.

## Operations, Admin, and observability

- The Scheduler exposes a stable `/scheduler/health` contract containing its
  application version, database/registry readiness, running state, job count,
  and sanitized diagnostic codes. Startup rejects a configured Scheduler
  replica count other than one for the supported SQLite topology.
- Admin adds clearer navigation, Scheduler health presentation, operational
  log-source status, safe handling of nullable persisted jobs, and a read-only
  Season Review built on the same completeness reporter as the CLI.
- A modular analytics framework records bounded upstream-poll and `/api/v1`
  request observations and daily rollups. Raw retention defaults to 14 days;
  reports are available through the checked-in reporting script and Admin.
- Diagnostics are opt-in and profile-based. Evidence tables and scripts remain
  distinct from production data and analytics.
- UTC match starts are normalized to one ISO-8601 representation, and
  same-season player membership refreshes preserve a previously resolved team
  when a later source snapshot cannot resolve one.

## Database migrations

The v0.6.0 head is `0015`. v0.7.0 adds the contiguous range `0016` through
`0024`, and **`0024` is the v0.7.0 migration head**:

| Migration | Purpose |
| --- | --- |
| `0016` | Diagnostic `matchItem` state observations. |
| `0017` | Diagnostic match-interchange observations. |
| `0018` | Diagnostic commentary polls and deduplicated events. |
| `0019` | Production commentary polls/events. |
| `0020` | Accepted player-stat history and period checkpoints. |
| `0021` | Production interchange observations, events, and poll outcomes. |
| `0022` | Canonical player/team identity on injury rows, with conservative backfill. |
| `0023` | Bounded analytics observations and daily rollups. |
| `0024` | Canonical CFS roster snapshots, selections, and change context. |

Migrations are forward-only, ordered, transactional, and checksum-verified by
the migration runner. Stop or drain writers and create a verified WAL-safe
backup before migrating. Rolling an application image back does **not** reverse
schema changes or writes made by the newer application; database restoration
is a separate, destructive operator decision. Follow the
[release runbook](../operations/release_runbook.md).

## Compatibility

Existing `/api/v1` contracts from v0.6.0 remain available; the release adds
resources and optional filters rather than removing or renaming existing v1
fields. Standard reads still require an active API key with `standard-read`.
Advanced provenance remains opt-in through `?advanced=true` and requires
`advanced-read`; keys created before capabilities were introduced retain the
migration-provided standard capability.

Unversioned `/api/...` routes remain compatibility routes over their existing
legacy persistence. They are not aliases for canonical v1 data. In particular,
legacy HTML `lineups` and `player_stats` remain separate from canonical CFS
rosters and player statistics. API clients must not combine those authorities
as interchangeable records.

The operator CLI remains compatible and `python cli.py --version` remains a
lightweight, database-free probe. Deployments must migrate before starting
application processes and must use exactly one Scheduler process with the
shared SQLite database.

## Remaining limitations

- AFL/CFS endpoints and rendered pages are upstream contracts outside this
  repository's control. Authentication, payload availability, identifiers,
  and page structure can change; fixture-backed tests do not guarantee future
  provider availability.
- The supported deployment boundary is one carefully operated SQLite database
  shared by API, Admin, and exactly one Scheduler. Horizontal Scheduler scaling
  and general multi-writer deployment are not supported.
- Source authority remains domain-specific, with no automatic cross-source
  fallback or dual-write. Legacy and canonical stores therefore can differ.
- Canonical links are deliberately nullable where provider identity cannot be
  resolved without guessing. Player same-season membership has no explicit
  upstream removal signal, so an unresolved refresh preserves the prior
  resolved team.
- Match rosters represent selections, not actual participation. Commentary and
  interchange availability is match/provider dependent, and analytics is
  operational telemetry rather than a billing or security audit ledger.
- Runtime API rate limiting is not implemented even though persistence has a
  nullable rate-limit field.

In v0.6.0, commentary, interchange, rosters, and canonical player resources
were listed as investigation-only or unavailable. Those limitations are stale:
the maintained capabilities above are now implemented. Diagnostic evidence
capture remains opt-in and is not itself a production data contract.

## Validation boundary

The release candidate should pass the complete offline automated suite, focused
version/API/migration checks, and the
[v0.7.0 pre-tag checklist](../operations/v0.7.0-pre-tag-checklist.md). Live
upstream calls are site-specific deployment validation, not a prerequisite for
building or testing this repository. The existing
[release-readiness review](../reviews/v0.7.0-release-readiness.md) remains its
original point-in-time assessment; a distinct final refresh against the exact
candidate SHA is still required before tagging.
