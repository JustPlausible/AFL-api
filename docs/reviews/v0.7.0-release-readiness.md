## 1. Executive summary

AFL-api has materially outgrown the two most recent written baselines (`docs/architecture/project_status_post_v0_5_0.md` and `docs/releases/v0.6.0.md`). Since the v0.6.0 release notes were committed (PR #172), 23 further PRs have shipped, promoting **commentary** and **interchange** from diagnostic-only evidence capture to production persistence and versioned consumer endpoints, adding canonical **player** lookup/search/season-navigation, adding canonical **injuries** with resolved identity, adding a **scheduler health** endpoint, an **admin Season Review** page, and a UTC start-time normalisation fix. The automated suite has grown from 397 tests at the v0.5.0 baseline, to "more than 700" at v0.6.0, to **1279 passing tests today**, all green in this run.

The two issues currently milestoned toward v0.7.0 — **#205** (a new modular analytics/telemetry framework) and **#199** (an internal CFS URL-modelling refactor) — are both, on inspection, non-blocking. Neither touches consumer-facing behaviour, data integrity, or operational safety; both explicitly say so in their own acceptance criteria, and #199 explicitly asks to be deferred by its own author. Their presence on the v0.7.0 milestone does not by itself make them release requirements, and this review does not treat it that way (see §5).

No release-blocking correctness, data-integrity, migration, or compatibility defect was found in this review. The main gap is **process/documentation debt**, not code: `version.py` still declares `0.6.0`, `README.md` and `docs/README.md` still say "Current version: 0.5.0", and no `docs/releases/v0.7.0.md` exists yet to record the substantial work done since v0.6.0. These are the primary items recommended before tagging a release (see §10).

## 2. Recommended release decision

**READY WITH MINOR ACTIONS.**

There is no architectural or consumer-API blocker. A small, bounded set of housekeeping work (version bump, release notes, README/docs reconciliation, milestone hygiene on #205/#199) should be completed before the release is tagged, but none of it requires new application code, schema changes, or behavioural changes. See §13 for the concrete release checklist.

**Can primary AFL-api feature development reasonably reduce now, while the API continues to be used by downstream consumer applications, treating remaining non-blocking work as maintenance/follow-up?**

**Yes.** The `/api/v1` consumer surface (§4) is coherent, internally consistent, defensively documented (explicit null-vs-empty and finality semantics throughout), fully covered by passing offline tests, and has had no breaking changes to previously shipped v1 resources in this cycle — only additive new resources and filters. Downstream consumer applications can begin (or continue) building against `/api/v1/seasons` → `rounds` → `matches` → `player-stats`/`commentary`/`interchanges`, plus `/api/v1/players` and `/api/v1/injuries`, today. The two open issues are forward-looking (telemetry) and internal-cleanliness (URL modelling) work respectively; neither is a reason to hold consumer application development, and neither is a reason to hold this release.

## 4. Consumer API readiness

`/api/v1` (`api/routes_v1.py`) is the versioned, consumer-facing surface. All routes require `x-api-key` (`auth.py`); `advanced=true` metadata additionally requires the `advanced-read` API-key capability and returns a structured `403` when absent.

**Resources implemented:**

| Resource | Endpoint | Notes |
| --- | --- | --- |
| Discovery | `GET /api/v1` | name/version/docs pointer |
| Seasons | `GET /api/v1/seasons` | `is_current`/`current_round_number` read directly from persisted sync state |
| Rounds | `GET /api/v1/seasons/{season_id}/rounds`, `GET /api/v1/rounds/{round_id}` | typed bye-team list; `null` vs `[]` explicitly distinguished (unavailable vs. confirmed-no-byes) |
| Matches | `GET /api/v1/rounds/{round_id}/matches`, `GET /api/v1/matches/{match_id}` | canonical home/away team identity only, resolved through `afl_teams` |
| Player stats | `GET /api/v1/matches/{match_id}/player-stats` | `lifecycle.finality`: `final`/`partial`/`not_available`, calculated from persisted evidence, not inferred from match status; `canonical_player_id`/`champion_data_player_id` filters are conjunctive and never cross-resolved (Issue #212) |
| Commentary | `GET /api/v1/matches/{match_id}/commentary` | chronological ordering despite upstream newest-first; `possible_edit_of_event_id` is heuristic and non-destructive; explicitly non-authoritative for finality/lifecycle/stats |
| Interchange | `GET /api/v1/matches/{match_id}/interchanges`, `.../interchanges/events` | current-state + event-history split; `on_bench` semantics confirmed against real Round 24 live evidence for LIVE/POSTGAME, with the one open `CONCLUDED` caveat documented directly in the field description (not hidden) |
| Players | `GET /api/v1/players/{canonical_player_id}`, `GET /api/v1/players?search=`, `GET /api/v1/players/{id}/seasons` | crosswalks (`afl_player_id`, `champion_data_player_id`) null rather than guessed; per-season team history never overwritten by a later season (PR #211) |
| Injuries | `GET /api/v1/injuries` | canonical identity only; unresolved rows omitted rather than exposed under an invented identity; a team's absence from the source page is explicitly documented as not meaning "zero injuries" |

**Assessment against the requested criteria:**

- **Endpoint correctness / identifier semantics:** Consistent single identifier model throughout — `season_id`/`round_id`/`match_id` are canonical AFL-api integers; `champion_data_player_id` is always opaque text; `canonical_player_id` is the internal `canonical_players.id`. No endpoint conflates these. Filters combining an unresolved/foreign identifier deterministically return an empty collection rather than an error or a guessed join (documented explicitly for player-stats and injuries filters).
- **Season/round/match/player relationships:** The full navigation chain (`seasons → rounds → matches → player-stats/commentary/interchanges`, and `players → seasons`) is implemented and cross-referenced in both directions (a player's `champion_data_player_id` is usable to filter match player-stats; a player's season membership links back to `GET /api/v1/seasons`).
- **Historical data behaviour:** Player season/team membership is scoped per season row, so a mid-career club change never rewrites history (verified directly in `_season_memberships`, `api/routes_v1.py:951`, and its own regression tests). Commentary and interchange retain full event history, not just current state.
- **Null vs. zero / empty semantics:** Deliberately and consistently distinguished throughout the module: `byes: null` (unavailable) vs. `byes: []` (confirmed no byes); an injuries team omitted from the source page vs. a team with zero current rows; a player-stats row with unresolved `canonical_player_id` (stays `null`, never guessed) vs. a genuinely absent player.
- **Match status representation:** `matches.status` remains the sole lifecycle authority (`docs/architecture/data_authority_map.md`); commentary/interchange/period-state are all explicitly documented as non-authoritative for it.
- **Pagination/metadata:** No pagination is implemented; collections are bounded by natural cardinality (one season's rounds, one round's matches, one match's stats/commentary/interchanges) except player search, which is explicitly capped at 100 rows (`MAX_PLAYER_SEARCH_RESULTS`) and documented as such. This is a reasonable, documented bound rather than a gap for the current resource shapes.
- **Compatibility of existing endpoints:** No breaking changes to previously shipped v1 response shapes were found in the 23-PR window reviewed; new resources and optional filters were added, consistent with the "strictly additive" statement at the top of `api/routes_v1.py`.
- **Could outstanding collector/admin/diagnostic work destabilise the API?** No. Both open issues (#205, #199) are explicitly scoped to avoid consumer/scheduler behavioural changes in their own acceptance criteria (see §5), and the diagnostic framework (§8) is architecturally firewalled from production reads (`docs/diagnostics_framework.md`'s stated core rule: "Diagnostic evidence must never silently become production source authority").

**Conclusion: the v1 API is sufficiently stable for downstream consumer application development to begin (or continue) now.** No known outstanding issue would corrupt, destabilise, or materially change consumer-visible behaviour of already-shipped v1 resources.

The one pre-existing, already-documented limitation worth restating for a downstream consumer: **lineups/rosters are not in `/api/v1`** (still legacy `/api/lineups/*`, HTML-sourced). A consumer application that needs lineup data must use the legacy compatibility route today; this is unchanged since v0.6.0 and not part of either open v0.7.0 issue.

## 5. v0.7.0 target issue assessment

### Issue #205 — "Add modular analytics framework for upstream collection and consumer API telemetry"

- **Purpose:** A new, optional observability layer measuring upstream polling efficiency and `/api/v1` resource usage, to inform future polling-cadence and API-roadmap decisions.
- **Current state:** Not started — no code, migration, or route exists for it in the current tree.
- **Affected subsystem:** New, additive cross-cutting layer (proposed common event contract + independently registered modules), explicitly modelled on the diagnostics framework's isolation pattern.
- **Consumer API impact:** **None.** The issue's own acceptance criteria and "Failure isolation" section require that analytics persistence failure "must not cause `/api/v1` requests to fail" and that it never alters match finality, snapshot authority, or source-selection rules.
- **Data-integrity impact:** None — the issue explicitly forbids storing full payloads and forbids treating unused data as evidence a collector should be removed.
- **Operational impact:** None today (unimplemented); if implemented per its own design, explicitly bounded and isolated from collection/serving paths.
- **Release risk if deferred:** None. This is forward-looking tooling to *inform* future decisions, not a fix for a present defect.
- **Recommendation: safe to defer indefinitely.** This is post-v0.7 (or later) work, not a v0.7.0 requirement. Its own priority/effort note even self-labels "P2/Medium," "not required for current API correctness," and recommends staging rather than one release.

### Issue #199 — "Refactor CFS URL modelling to use /cfs as the service root"

- **Purpose:** Internal renaming/restructuring of how CFS endpoint base URLs are modelled in code (`CFS_API_BASE` → distinguishing a true `/cfs` service root from the `/afl` endpoint family), so the existing `commentaryFeed` special-case override is no longer needed.
- **Current state:** Not started as a refactor, but the underlying problem is already **functionally resolved**: PR #198 (already merged, in `main`) added `EndpointDefinition.base_url_override` (`afl_json/contracts.py:60-77`), which correctly resolves `commentaryFeed` outside the `/afl` root today. Verified directly in code: `CFS_API_BASE` is a hardcoded `Final` Python constant (`https://api.afl.com.au/cfs/afl`), not an environment variable — so there is no operator-facing configuration exposed for this at all, and the "compatibility/migration" risk the issue raises about breaking a previously valid `.env` does not currently apply.
- **Affected subsystem:** Internal endpoint-definition modelling only (`afl_json/contracts.py`).
- **Consumer API impact:** **None** — the issue's own acceptance criteria require "No consumer API behaviour changes" and "No scheduler behaviour changes," and every currently maintained endpoint must resolve to the exact same URL after the refactor.
- **Data-integrity impact:** None.
- **Operational impact:** None — this is a naming/structure cleanup of already-working code.
- **Release risk if deferred:** None.
- **Recommendation: safe to defer.** The issue explicitly says so itself: *"Do not prioritise this over the current Round 24 diagnostic collection... Revisit this after the match weekend, when the working match-clock/interchange/commentary diagnostics have been validated and there is no live-data benefit to changing shared URL construction."* Its own "Timing" section places it after live-match work is done, not before a release. It is genuinely useful engineering hygiene "before the 2027 season," not a v0.7.0 requirement.

**Milestone note:** Neither issue's presence on a `v0.7.0` GitHub milestone was treated as evidence of blocking status, per this review's instructions — both were independently assessed against actual consumer/data/operational impact and found non-blocking on that basis, not on the milestone label. It would be reasonable for the maintainer to move both off the `v0.7.0` milestone (or explicitly retarget them to a future one) to keep the milestone an accurate release-scope signal going forward — this review makes no change to the milestone itself.

## 8. Operational/diagnostic readiness

Assessed against the specific questions posed, distinguishing what is needed for *safe operation* from what is *useful for future development*:

- **Can collection failures be identified?** Yes. `scrape_runs` records lifecycle/outcome/redacted-error per collection attempt across every domain (metadata, players, stats, commentary, interchange, injuries); `docs/scrape_run_audit.md`.
- **Can scheduler failures be identified?** Yes. `GET /scheduler/health` (PR #190, `docs/scheduler_health.md`) gives a stable `healthy`/`starting`/`unhealthy` contract with sanitised diagnostic codes, distinct from job-count noise (an empty-but-healthy scheduler is explicitly not "unhealthy"). Surfaced in the Admin Schedule page.
- **Can malformed/incomplete data be investigated?** Yes, at two levels: the diagnostics framework (`match_clock`, `interchange`, `commentary` profiles — opt-in, evidence-only, never a production read path) for upstream-shape uncertainty, and `SeasonCompletenessReporter` (`python cli.py --report-afl-season`, now also an Admin page — PR #215) for read-only season/round/match/stat/membership completeness checking.
- **Is season bootstrap/refill behaviour reliable?** The bootstrap → sync → report sequence (`--bootstrap-afl-season`, `--sync-afl-season`, `--report-afl-season`) is unchanged in contract since v0.6.0 and remains covered by dedicated tests (`test_afl_season_sync.py`, `test_afl_season_report.py`, `test_cli_player_season_bootstrap.py`); PR #185 additionally hardened current-season marker maintenance during bootstrap/sync.
- **Can live-match data collection be observed?** Yes — `/scheduler/match-windows` exposes per-match lifecycle/phase/lease/attempt/finality state; the diagnostics profiles provide raw-evidence capture during live play when explicitly enabled.
- **Do consumer API regressions have meaningful automated coverage?** Yes — every `/api/v1` resource has its own dedicated test module (§7), and all are green.

**Distinguishing operational necessity from development convenience, as requested:** the scheduler-health endpoint, scrape-run audit, and season-completeness reporting are operational-safety tooling and are already in place. The diagnostics framework and the not-yet-built analytics framework (#205) are development/investigation tooling; their completeness is not a precondition for safe v0.7.0 operation, consistent with §5's assessment of #205.

## 12. Risks and known limitations

- **Upstream contract stability.** AFL/CFS endpoints have no public compatibility guarantee; fixture/contract tests protect against regression on the *observed* contract but cannot prevent upstream schema, auth, or availability changes. This is an ongoing operational reality, not a v0.7.0-specific risk.
- **Single-instance SQLite architecture.** Unchanged since v0.6.0: one shared database, one Scheduler process, serialized writes. This is a known, documented, and accepted architectural boundary, not a defect.
- **No runtime rate limiting.** Acceptable for a small number of known consumer applications today; would need attention before opening the API to untrusted third parties.
- **No usage/efficiency telemetry.** Polling-cadence and endpoint-value decisions currently rely on judgement rather than measured evidence; Issue #205 exists to address this but is explicitly non-blocking.
- **Interchange `CONCLUDED` semantics** are the one explicitly-flagged open evidence question in an already-shipped v1 resource (`on_bench` for `CONCLUDED` matches) — documented transparently in the API's own field description rather than hidden, and does not affect LIVE/POSTGAME behaviour, which is where a real-time consumer application's use cases would primarily apply.
- **Live-environment verification gap in this review.** This review could not exercise live AFL/CFS network calls or the Docker/Compose stack from its own sandbox; this is a pre-existing environment constraint (also hit by the 2026-08-24 injury investigation) and not evidence of an application defect. Operators should still perform live-validation steps before/after tagging the release, using an updated runbook rather than `release_runbook_v0_5_0.md` as-is (§10 item 5, §13 item 5).

1. `version.py` declares `0.7.0`; `README.md`/`docs/README.md` version text matches.
2. `docs/releases/v0.7.0.md` exists and accurately summarises the cycle (§10.2).
3. Full automated suite passes (already true: 1279/1279).
4. `#205` and `#199` are explicitly acknowledged as non-blocking/deferred in their milestone status (§10.3), or moved to a later milestone.
5. A **version-neutral or v0.7.0-specific** release runbook exists and is followed for backup, migration application through `0022`, and post-upgrade verification (`--report-afl-season`). **Do not** execute `docs/operations/release_runbook_v0_5_0.md` as written against a v0.7.0 database: its STOP gates require exactly migrations `0001`–`0011` (count 11), which a v0.7.0 upgrade will not match (§10 item 5).
6. No new migration, schema, or `/api/v1` contract change is introduced between this review and the tag beyond what has already been reviewed here.

## 14. Conclusion

**Overall recommendation: READY WITH MINOR ACTIONS.**

AFL-api's collection/persistence pipeline, scheduler, canonical data model, diagnostics tooling, admin surface, and versioned consumer API are all substantially complete, internally consistent, and backed by a large and currently fully-passing automated test suite (1279/1279). The two issues carrying the v0.7.0 milestone are both genuinely non-blocking on independent inspection of their actual scope and acceptance criteria — one is unstarted future telemetry work, the other is an internal naming refactor whose underlying problem is already patched in production. No release-blocking defect was found. The only outstanding work is version/documentation housekeeping (§10), which is small, bounded, and does not require further application development.

**On reducing primary AFL-api feature development while the API is used by downstream consumers:** reasonable, and recommended. The `/api/v1` surface reviewed in §4 is a dependable boundary today — consistent identifier semantics, explicit null-vs-empty/finality handling, no undocumented breaking changes across this review's 23-PR window, and full regression coverage per resource. Remaining AFL-api work (§11, plus the §10 housekeeping) can proceed as maintenance/follow-up alongside downstream consumer application development without putting the v0.7.0 boundary at risk.

### F6. Canonical persistence and data integrity — final, with specific roster-persistence verification

Original §3/§9 findings for seasons/current-season state, teams/team-season participation, canonical players, provider mappings, historical player membership, rounds/matches, and authoritative stat persistence are unchanged and re-confirmed present in the current tree (`afl_json/`, `db/migrations/0001`–`0022`).

- `persist_match_rosters` gates on `result.status is RosterStatus.PUBLISHED` at the top; an `UNAVAILABLE` (top-level `null`) or `EMPTY` (top-level `[]`) round observation returns immediately without touching any of the three roster tables (`afl_json/rosters.py:228`–`229`).
- A malformed/partial response never reaches `persist_match_rosters` at all — `MatchRosterCollector.collect`/`_normalise_rosters` raises `AflJsonInvalidResponse` before a `RosterCollectionResult` is constructed, so the caller never invokes persistence for that observation.
- **Per-collection, not just per-round, non-destructiveness is enforced.** `replacement_authoritative_collections` is computed per team, per field, as "only an observed **list** has verified replacement semantics" (`_normalise_team`, `afl_json/rosters.py:606`–`634`). `persist_match_rosters` only calls `_replace_selections` when `"positions" in authoritative`, and only calls `_replace_context` for a given `context_type` when that specific type is in `authoritative` (`afl_json/rosters.py:294`, `312`–`313`). This means a null/absent/malformed-shape `positions`, or a null/absent/malformed-shape `ins` (independent of `outs`, `lateChanges`, etc.), each individually leave the corresponding previously-persisted table rows completely untouched — exactly the granularity Issue #219's own scope required ("Do not treat an empty list as destructive replacement authority unless current evidence proves that meaning"). This is independently verified by 6 dedicated tests in `tests/test_match_roster_production.py`: `test_non_list_positions_observation_preserves_prior_selection` (parametrized over `None`/dict/malformed shapes), `test_missing_positions_observation_preserves_prior_selection`, `test_non_list_context_observation_preserves_prior_collection`, `test_null_unavailable_observation_does_not_erase_prior_valid_roster`, `test_empty_list_observation_is_conservatively_non_destructive`, `test_malformed_response_never_reaches_persistence` — all passing in this review's run.
- An unresolved canonical match skips only that match (`unmatched_matches`), never blocking the rest of the round's matches from persisting; an unresolved canonical team still persists the roster/selection/context rows with `canonical_team_id=NULL` rather than discarding the observation, and self-heals on a later observation once a crosswalk resolves (`resolve_canonical_player`/`resolve_canonical_team`, re-resolved on every write) — verified directly and by `test_later_crosswalk_self_heals_unresolved_canonical_player`, `test_unmatched_canonical_team_still_persists_provider_identity`, `test_unmatched_canonical_match_is_skipped_without_affecting_persistence_call`.
- No guessed identity: a selection/context record with no Champion Data player id is skipped rather than persisted under an invented identity (`_replace_selections`/`_replace_context` only iterate `records` already filtered to `champion_data_player_id` truthy in `persist_match_rosters`), and no name/jumper-number-based join exists anywhere in `resolve_canonical_player`.
- Legacy `lineups` table/routes are untouched by migration `0024` and by `afl_json/rosters.py` — verified by absence of any reference to the `lineups` table in either file, consistent with `docs/architecture/data_authority_map.md`'s explicit statement that the two remain independent authorities with no fallback or dual-write.

**One minor, non-blocking observation** (not in Issue #219's own test list, and not a destructive-erasure defect): `_normalise_rosters` derives the *round-level* `RosterCollectionResult.status` by checking whether **any** individual match's `matchRoster.status` string equals `"unavailable"`, `"unpublished"`, or `"not_published"` (case-insensitive) across the whole round payload (`afl_json/rosters.py:595`–`597`). If a provider round response ever contained a mix of matches with genuinely published rosters alongside one match carrying one of those literal per-match status strings, the current code would treat the **entire round observation** as `UNAVAILABLE` and skip persistence for every match in that round for that poll, not just the affected match. This is conservative/fail-safe, not destructive — no previously persisted roster is erased, and a subsequent poll (15-minute cadence) would still pick up the previously-blocked matches once resolved. It is also speculative code: the only per-match `matchRoster.status` values actually observed in committed live evidence are `UNCONFIRMED_TEAMS`, `LIVE`, and `CONCLUDED` (`docs/match_rosters.md`); none of the three literal strings this branch checks for has been observed as a per-match status value (the documented `unavailable` semantic applies to the round's top-level JSON `null`, a structurally different signal already handled earlier in the same function). No test in the roster suite exercises a multi-match round payload with mixed per-match statuses. **Recommendation: track as a documented known limitation (§F12), not a release blocker** — it cannot corrupt or erase data, and it defends against a currently-unobserved provider shape rather than a proven-wrong one.
